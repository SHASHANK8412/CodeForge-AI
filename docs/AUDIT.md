# AIForge feature audit

This is a status-by-evidence audit of AIForge against the 15-feature target spec. Statuses:

- **Verified**: implemented, and an automated test in this repo exercises it end to end.
- **Implemented**: real code, but no end-to-end test (or it needs Ollama, Docker or cloud credentials to check).
- **Partial**: real code that covers only part of the feature.
- **Simulated**: code exists, but it fakes the result (fixed success values, invented output, `sleep` standing in for work). These must not be presented as features until they're replaced.
- **Missing**: not implemented.
- **Not audited**: not inspected closely enough to classify.

Last updated with the commit that added `backend/execution/repair_policy.py`.

## What this means for the resume

Claim only rows marked Verified, or Implemented with a benchmark number behind them. Specifically:

- Don't list cloud deployment, multi-provider routing, or SRE auto-recovery until the simulated modules are replaced or removed. In an interview, "it says it called GPT-4o but it didn't" is worse than not having the feature.
- The self-healing loop and the evaluation harness are the strongest, most defensible pieces. Both have end-to-end tests and produce evidence.

## Prioritized plan

1. **Get the numbers.** Run the 20-task benchmark with the default models, `--llm-repair off`, and one other model (`docs/EVALUATION.md`). This turns rows 3 and 14 into resume lines.
2. **Remove or clearly label the simulated modules** (`llm/litellm_gateway.py`, `llm/model_manager.py`, `llm/vllm_engine.py`, `rag/qdrant_store.py`, `deployment/pipeline.py`, `monitoring/recovery_engine.py`) and any UI that displays their output as real.
3. **One real cloud provider behind the router** (an OpenAI-compatible endpoint covers OpenAI, Groq and many hosts), with real token and cost tracking. Then the benchmark can answer "local vs. cloud" with data.
4. **Repository mode:** run the existing `RepositoryIndexer` + the self-healing loop on an *existing* repo ("fix this failing test"). It reuses the sandbox, the repair policy and the verification report, and adds bug-fixing tasks to the benchmark.
5. **One real deployment target** (e.g. build and run the project's Docker image locally, then health-check it), with user approval before anything billable.

Items 2–5 each need their own design pass; they aren't small edits.
